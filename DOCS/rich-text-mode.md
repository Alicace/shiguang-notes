# 富文本模式：官方实现与增加方案

日期：2026-10-15（同日更新：加入官方网页版源码核查）。范围：调研官方拾光便签的实现方式、本项目现有编辑链路，给出可选方案与取舍。本文只做方案，不改变现有行为。

## 0. 先明确一件事

本项目**还没有富文本模式**，只有这份方案。所以「和官方一样吗」只能比较方案与官方，不能比较成品。下面的源码核查说明：官方与最初设想的「Markdown + 双向映射」路线在底层结构上**并不相同**。

## 1. 官方实现（网页版源码核查）

核查对象：<https://cloud.smartisan.com/apps/note/>（AngularJS 应用 `ng-app=noteApp`）及其脚本 `note-app_5edb5c68aa.js`。

**编辑器内核是 CodeMirror，不是 contenteditable。** 代码里是 `CodeMirror(document.getElementById("editor"), { lineWrapping: true, cursorHeight: .4, ... })`、`editor.getCursor()`、`EditorService.setCursor({line: 0, ch: 100})`、`cm.replaceSelection("\n", "end")` 这类 CodeMirror API；便签编辑器是 `#editor`，另有 `#editorcopy0..2` 三份切换动画用的副本。

**每篇便签自己保存排版模式。**

```js
app.filter("modeName", [function () { ... var nameMap = ["无", "富文本模式", "Markdown 模式"]; ... }])
0 === note.formatting_mode && TypoService.typo(note.detail)
1 === note.formatting_mode && TypoService.rtf(note.detail, note.rtf_style)
2 === note.formatting_mode && TypoService.markdown(note.detail)
server.FORMATTING_MODE = "formatting_mode"
```

模式是 `formatting_mode`：`0` 纯文本、`1` 富文本、`2` Markdown，随便签数据保存；分享接口提交 `{ title, content: note.detail, sync_id, rtf_style, formatting_mode }`。切换模式不产生第二份内容，因为文本始终在 `note.detail` 里。

**富文本 = 纯文本 + 样式区间，不是 HTML。**

```js
_blockStyles = [HEAD, UL, TODO, "todo_checked", QUOTE, "image", NORMAL]
_inlineStyles = ["bold", "normal_in"]
_concatStyles = [UL, TODO, "todo_checked"]
_alignStyles = ["center", LEFT]
```

样式以行内/行级/块级标记叠在文本缓冲区上（`addStyle`、`RtfService.setStyleData(editor, styleData, noteContent)`、`.rtf-todo` 与点击 `.line-todo` 切换待办），渲染时加对应 class，而不是保存富文本 HTML。这套样式词表与用户提供的官方网页截图工具栏完全对应：标题 H、居中、列表、加粗、引用、复选框。

对照来源：官方 Markdown 说明页 <https://cloud.smartisan.com/apps/note/md.html>（网页版在左上角菜单用「开启 Markdown 功能」开关）；官方 2.5 版本发布说明；官方移动端功能说明（工具栏含字号 A±、加粗、斜体、下划线、待办、插入图片）。移动端的字号/斜体/下划线同样是样式层能力，属于网页版之外的扩展。

## 2. 本项目现状

上游 zhaoolee/notes 是**只有 Markdown 一条链路**的复刻，本项目沿用该结构：

- 数据模型只有 `NoteDocument.markdown: string`（`src/types/app.ts`），没有模式字段也没有样式数据；同步、归档、Skill/DSH 接口都读写这个字段。
- 编辑区是分段的 `textarea`（`src/components/EditorPanel.tsx`，含选区镜像层、图片导入与标注、输入法处理），视图切换只有「Markdown 模式 / 实时预览」两档（`src/App.tsx` 的 `DesktopWorkspaceView`）。
- 渲染是 `react-markdown` + `remark-gfm`（`src/lib/markdown.ts`、`NoteSheet.tsx`）；我们的 Markdown 方言已经覆盖官方富文本的样式集合（含 `[文字]` 居中 → `headingAlignment: "center"`），但**格式信息存在文本里**，没有独立样式层。
- 导出与分发全部从 Markdown 派生：客户端 PNG 走预览 DOM → `html-to-image`；公众号 HTML 走 Markdown AST（`src/lib/wechat-markdown.ts`）；离线归档、Skill/DSH 生成便签都是 Markdown 文本。

因此「加富文本模式」的真正问题是：**要不要把「格式」从文本里拆出来**。不拆，就是方案 A（界面像、能力受 Markdown 限制）；拆，就是 B′（与官方同构）。

## 3. 四种可选实现

| 方案 | 做法 | 与官方的关系 | 改动面 | 工作量 |
| --- | --- | --- | --- | --- |
| A 所见即所得，Markdown 是真源 | `contenteditable` 编辑面，Markdown ⇄ 可编辑 DOM 双向映射 | 只是「看起来像」：内核是浏览器富文本 DOM，格式靠 Markdown 语法表达 | 前端新增编辑器与映射；存储、同步、导出不动 | 中（第一阶段约 300–600 行 + 测试） |
| **B′ 文本 + 样式区间 + 每篇模式（对齐官方）** | 便签增加 `formattingMode` 与样式数据（行内/行级/块级标记），文本仍是纯文本/Markdown；在文本编辑器上叠加样式层，工具栏直接改样式 | **结构上最接近官方**：同一份文本、样式独立、模式随便签保存、切换模式不丢格式 | 数据模型、同步协议、PNG/公众号/归档导出、Skill 接口都要感知模式与样式，旧便签需要默认模式迁移 | 大（含跨端与接口兼容） |
| B HTML 双格式 | 增加 HTML 字段，富文本直接存 HTML | 行为像，但官方存的是样式区间而非 HTML，导出与公众号要解析 HTML，保真更难 | 比 B′ 更大 | 大 |
| C 只加工具栏，继续写 Markdown | 保持 `textarea`，按钮在光标处插入 `#`、`**`、`- [ ]` 等语法 | 只有工具栏外观像，不是富文本 | 只在 `EditorPanel` 加按钮与快捷键 | 小（半天） |

## 4. 怎么选

**要「和官方一样」→ 选 B′。** 官方那套的关键不是界面，而是「文本缓冲区 + 独立样式数据 + 每篇便签的 `formatting_mode`」。只有按这个结构实现，切换模式才不会丢格式，导出与公众号才能同时吃到文本与样式，字号、下划线这类 Markdown 表达不了的能力才有地方放。代价是数据模型和导出链路都要改，并要处理旧便签默认模式与跨端兼容（飞牛侧旧包、Skill/DSH 接口目前都按 Markdown 文本工作）。

**只想要「看上去像官方」→ 选 A。** 界面与工具栏可以做得几乎一致，存储与导出零改动，风险集中在双向映射与往返保真；但能力上限就是 Markdown 能表达的范围，官方移动端的字号 A±、斜体、下划线无法忠实表达（强行做就要给 Markdown 扩语法，实际上又滑向 B′）。

**只想先给按钮 → 选 C**，作为过渡。

原建议偏 A，是因为当时判断「官方也是 Markdown 与富文本并存、文本为主」；源码核查后这个判断需要修正：官方的富文本有独立样式层，A 只能近似，不能等价。

## 4.1 如果选 A：分两阶段

### 第一阶段：富文本编辑面（Markdown 真源不变）

1. 视图三档：`DesktopWorkspaceView` 增加 `"rich"`，顶部下拉变成「富文本模式 / Markdown 模式 / 实时预览」。默认仍是 Markdown 模式，避免改变现有用户习惯；如需对齐官方默认值，可后续单独调整（这是一处产品取舍，需你确认）。
2. 新增 `src/components/RichTextEditor.tsx`：`contenteditable` 编辑面，复用便签纸张样式，让它与预览的排版接近；图片仍走现有 `editor-images.ts` 的导入与标注入口。
3. 新增 `src/lib/rich-text.ts`：双向映射
   - `markdownToEditableHtml(markdown)`：把现有 Markdown 子集渲染成可编辑 DOM（标题、段落、居中块、引用、有序/无序列表、待办复选框、图片、粗体/斜体）。
   - `editableHtmlToMarkdown(html)`：把 DOM 变回 Markdown，集中处理空行（项目已有的 `preserveMarkdownBlankLines`、`MARKDOWN_BLANK_LINE` 规则必须复用，否则公众号空行修复会被破坏）。
   - 未支持的语法（代码块、表格、脚注等）原样保留为文本节点，避免静默丢内容。
4. 工具栏按官方配置：标题 H1/H2/H3、居中、有序/无序列表、加粗、引用、待办复选框；操作走 `document.execCommand` 的等价实现或自建 Range 操作，并提供撤销/重做。
5. 保存时机：与 Markdown 模式一致——输入防抖后写工作区，`Cmd/Ctrl+S` 立即保存；模式切换时先落盘再换面，避免两套状态互相覆盖。
6. 粘贴处理：默认按纯文本粘贴，或在白名单内保留 `strong/em/ul/ol/li/blockquote/h1-h3/img` 后转 Markdown，防止外部 HTML 直接注入编辑面。

第一阶段的边界：手机端先保持现状（Markdown 模式 + 预览），富文本面先在桌面与平板落地；编辑器内的图片裁剪、AI 审阅、分享与导出面板继续复用。

### 第二阶段（可选）：能力对齐

- 官方移动端的字号 A+/A-、斜体、下划线：字号可用 Markdown 无法表达的方案（内联 HTML 或自定义语法）承载；如果要做，需要在 `wechat-markdown.ts` 与 PNG 渲染里同步支持，属于对导出链路的扩展，建议单独一期。
- 若自研映射的边界处理成本过高，可切换到 TipTap/ProseMirror + Markdown 序列化（同样保持 Markdown 真源），届时只替换 `RichTextEditor` 内部实现。

## 5. 任一方案都要过的验收

- 模式切换不丢内容也不丢格式：同一篇便签在纯文本 / 富文本 / Markdown 之间往返、刷新、跨端同步后结果一致；B′ 还要覆盖旧便签的默认模式。
- 导出与分发一致：PNG、公众号复制、单篇与整包归档、Skill/DSH 生成便签在三种模式下都不丢格式信息（A 靠往返稳定，B′ 靠导出同时读样式与文本）。
- 不丢内容：代码块、表格、脚注等未支持构造在编辑面与导出中都原样保留。
- 真实浏览器：`fnos/native/ui-browser-check.js` 增加模式切换、工具栏操作与刷新后内容保持的断言。
- 输入法：沿用 `scripts/benchmark-input-latency.mjs` 基线，确认中文输入不劣化（自绘样式层与 contenteditable 都要测）。

## 6. 结论

官方富文本模式的底层是「一份文本 + 一套独立样式数据 + 每篇便签自己的排版模式」，编辑内核是 CodeMirror；本项目现在是纯 Markdown 单一真源。方案 A 能让界面与工具栏像官方，但底层构造不同，能力上限受 Markdown 限制；要和官方一致就得走 B′，这会改动数据模型与全部导出链路。选哪条需要先定，再开工。

## 7. 第一阶段已落地（0.4.0）

按 B′ 落地第一片，目标是先把数据与导出链路做对：

- 数据模型：`NoteDocument` 增加 `formattingMode`（`plain` / `rich` / `markdown`，对应官方 `0/1/2`）与 `richText`（`text` + `lineStyles` + `inline`）。旧便签读回时视为 `markdown`，行为不变。
- 转换内核 `src/lib/rich-text.ts`：`markdownToRichText` / `richTextToMarkdown` 双向转换、样式操作（标题级别、居中、列表、待办、引用、加粗）、编辑后样式归一、存储校验。未识别的构造（代码块、表格等）原样保留，切换模式不丢内容。
- Markdown 视图：富文本便签的 `markdown` 字段由文本与样式实时派生，预览、PNG、公众号、归档、搜索、Skill 全部沿用原有链路，一行都不用改。
- 界面：便签状态栏新增官方同名的排版模式开关（纯文本 / 富文本模式 / Markdown 模式）；富文本模式下编辑器底部出现官方按钮集合（标题、居中、列表、待办、加粗、引用），同一组按钮在 Markdown 模式仍插入语法，与官方「一套工具栏、两种作用」一致；原来的视图开关从「Markdown 模式」改名为「编辑」，避免与排版模式混淆。

### 与官方仍不一致的地方

| 项 | 官方 | 本项目当前 | 状态 |
| --- | --- | --- | --- |
| 编辑内核 | CodeMirror + 样式层 | 分块 textarea（自动换行、图片块、镜像层） | 未改，第二阶段 |
| 排版模式 | 每篇便签 `formatting_mode` 0/1/2 | 同名状态与开关 | 已对齐 |
| 富文本数据 | `detail` + `rtf_style` | `text` + `lineStyles` + `inline` | 结构对齐，字段名不同 |
| 样式词表 | HEAD/UL/TODO/todo_checked/QUOTE/image/NORMAL + bold + center/left | 同集合，另加 `ol`（Markdown 模式下已有有序列表，不能因此丢结构） | 基本对齐，多一项 |
| 标题与列表叠加 | 允许叠加（`_allowOverlap`） | 互斥，后设的样式清除另一个 | 有意偏离：Markdown 视图无法表达 `# - 文字` |
| 居中 | 任意行 | 仅便签首行（渲染层限制），其他行的居中标记保留在数据里 | 部分实现 |
| 模式开关位置 | 编辑器状态栏 | 便签状态栏（同一语义位置） | 已对齐 |
| 编辑时样式可见 | 是 | 否，样式在预览/PNG/公众号中生效 | 未实现，第二阶段 |
| 待办勾选 | 点击复选框切换 | 工具栏循环「无 → 待办 → 已完成 → 无」 | 部分实现 |
| 字号 A±、斜体、下划线 | 移动端有 | 无 | 未实现 |

### 已知限制

1. **样式按行号绑定**：在中间插入或删除行时，行样式不会自动跟随移动。官方用 CodeMirror 的行标记解决；本阶段靠编辑后归一（越界样式裁剪、行数变化裁剪）避免错位，第二阶段换编辑内核时一并解决。
2. **编辑面不含所见即所得**：富文本模式下编辑器显示纯文本，排版效果在实时预览与导出中呈现。这样做是为先把数据与导出链路做对，同时避免在 textarea 上用透明文字叠加样式层带来的输入法不可见、字体度量不一致等风险。
3. **居中与叠加样式**：见上表，属于渲染层能力的差距，不是数据缺失。
4. **默认模式仍是 Markdown**：官方新建便签默认富文本。等编辑面具备所见即所得后，把 `createNoteDocument` 的默认值改成 `rich` 即可（一行）。现在默认保持 Markdown，避免新便签的排版行为倒退。

### 验证

- `frontend/tests/rich-text.test.ts`：12 项，覆盖双向转换、样式操作、互斥规则、越界裁剪、存储校验、工作区读写兼容、工具栏与模式开关契约。
- `fnos/native/ui-browser-check.js`：真实浏览器点击「切换排版模式 → 富文本模式」，用键盘选中末行加粗、逐行设置待办与标题，断言编辑文本未被改动、预览出现 `strong` / 复选框 / 标题，再切回 Markdown 模式确认语法往返（`# 标题行`、`- [ ] 列表行`、`**正文行**`）。

## 8. 第二阶段已落地（0.5.0）

按 B′ 换上官方同思路的编辑内核，解决第一阶段最痛的两点：样式看不见、样式钉在行号上。

- 依赖：新增 `@codemirror/state`、`@codemirror/view`、`@codemirror/commands`（官方网页版用的是 CodeMirror，这一版与之同源同代）。
- 新组件 `src/components/RichTextEditor.tsx`：富文本模式不再使用文本域，改用 CodeMirror 编辑面；行样式（标题级别、无序/有序列表、引用、居中、待办）以行装饰呈现，行内加粗以字符区间标记呈现，待办是可直接点击的复选框控件。
- 样式跟随编辑：样式状态保存在编辑器状态里（`src/lib/rich-editor-state.ts`），编辑时通过 `ChangeSet.mapPos` 映射——在标题前插入新行，标题样式跟着标题文字走，而不是留在空行上；删除行、拆分行同理。这是第一阶段「样式按行号绑定」限制的正解。
- 工具栏：H / 居中 / 列表 / 待办 / 加粗 / 引用 六个按钮保留，改为对编辑器选区生效；`Mod-B` 也能加粗（光标无选区时取所在单词）。Markdown 模式仍由原编辑器插入语法，两套互不影响。
- 回写仍然归一：编辑器把 `text + 行样式 + 行内样式` 交给应用层，再由 `richTextToMarkdown` 派生预览、PNG、公众号、归档与 Skill 用的 Markdown，导出链路一行未改。

| 样式跟随编辑 | 是（行标记） | 是（`ChangeSet.mapPos`，有单测） | 已对齐 |
| 编辑时样式可见 | 是 | 是（标题/列表/引用/待办/加粗/居中） | 已对齐 |
| 待办勾选 | 点复选框 | 点编辑面里的复选框（无 → 待办 → 已完成 → 无） | 已对齐 |
| 居中 | 任意行 | 编辑面任意行可见；Markdown 视图（预览/PNG/公众号）仍只支持首行标题居中 | 渲染层仍待扩展 |
| 图片 | 编辑面内嵌图片块 | 富文本编辑面用图片按钮插入 `![](…)` 文本行，预览与导出正常；Markdown 模式仍有图片块、裁剪与标注入口 | 富文本面待补图片块 |

| 富文本粘贴 | 保留样式 | 按纯文本粘贴（未做 HTML → 样式转换） | 未实现 |

### 代价与限制

1. 前端包因为 CodeMirror 增大（压缩后 620 KB → 904 KB，gzip 约 +85 KB）。
2. 富文本模式的编辑面与 Markdown 模式的编辑面是两套实现，图片块、移动端悬浮光标等 Markdown 侧的能力暂未在富文本侧复刻。
3. 居中在渲染层（预览/PNG/公众号）仍只覆盖便签首行，需要在渲染层支持任意行居中后才能完全对齐官方。
4. 默认模式仍是 Markdown；等移动端富文本面验收后再决定是否改成官方默认的富文本。

## 9. 第三阶段已落地（0.6.0）

补齐第二阶段遗留的差异项：

- **任意行居中（渲染层）**：官方用一对中括号 `[文字]` 表示居中一段文字，可放在任意行、也可与标题叠加。渲染层（`MarkdownText` 的 remark 插件）现在把这样的整行渲染成居中段落，预览、PNG、离线归档共用同一份结果；公众号在 `WechatArticle` 里写成内联 `text-align:center`（微信只保留内联样式）。富文本的 `center` 样式因此可以落在任意行，序列化为 `[文字]` / `[# 文字]`；居中与列表/待办/引用互斥（Markdown 无法表达「居中的列表项」，后设的样式让另一个让位）。
- **富文本面的图片块**：编辑面里的 `![](…)` 行不再显示成文本，而是渲染成图片块（CodeMirror 行级 `Decoration.replace`），预览与导出仍走原有图片渲染；Markdown 模式保留原有的图片块、裁剪与标注入口。
- **斜体**：样式词表加入 `italic`（对应官方 `_inlineStyles` 的斜体），编辑面以 `rtf-italic` 呈现，序列化为 `*文字*`，反解时与加粗一样拆成字符区间。一段文字只保留一种行内样式：给一段已斜体的文字加粗，重叠部分归新样式，另一段保持斜体（Markdown 不生成有歧义的嵌套强调）。
- **移动端工具栏**：390 px 视口下富文本工具栏不再隐藏，七个按钮（H / 居中 / 列表 / 待办 / 加粗 / 斜体 / 引用）都在窗口内，已加入浏览器检查断言。
- **待办行**：编辑面里待办行只显示复选框，不再同时显示列表圆点。

## 10. 第四阶段：字号档位与下划线（0.7.0），以及一次自我纠正

动手前重新核对了官方网页版脚本，结论修正了两条我先前写错的差异项：

- **官方网页版没有粘贴富文本处理**：`note-app_5edb5c68aa.js` 里 `clipboardData` 出现 0 次，`paste` 只做文本规整。所以「富文本粘贴保留样式」**不是差异**，第 8 节的这一行已作废（本项目同样按纯文本粘贴，与官方网页版一致）。
- **官方网页版没有字号 A±**：脚本里 `fontsize` / `font-size` 出现 0 次，富文本样式类只有 `rtf-concat` / `rtf-preview` / `rtf-todo`；A± 与下划线都只存在于移动端。因此原先设想的 `{s:0.85}文字{/s}` 这类**逐段字号语法是错的设计**——A± 没有选区语义，它是整篇便签的字号档位。

### 本轮实现

- **便签字号档位（对齐移动端 A± 的语义）**：便签新增 `fontScale`（小 0.85 / 标准 1 / 大 1.15 / 特大 1.3），桌面状态栏与手机详情栏都有 A− / A+，边界不可再点。它作用于**整篇**：编辑器字号与行高（横线纸节奏一起缩放）、预览与 PNG 的正文（只缩放正文，纸张与边框保持原尺寸）、公众号的内联 px 字号（正文与各级标题一起乘系数）。读写时非法值回落到标准档。
- **下划线**：行内样式词表加入 `underline`，工具栏第八个按钮与 `Mod-U`，编辑面以 `rtf-underline` 呈现。存储语法沿用 Markdown Extra 的 `++文字++` 约定（`<ins>` 语义），并带 flanking 规则：`i++ 与 j++`、`C++ 很好`、`a+++b`、`++ 前后有空格 ++` 都保持原文，不会被误判。渲染层把 `++…++` 变成 `<u class="markdown-underline">`（预览、PNG 共用），公众号写成内联 `text-decoration:underline`。
- **行内样式解析重写**：原先三段串行剥离会让后一段的标记位移算错（前一段剥掉的字符会移动后面的位置）。现在改为单趟扫描 + 对内容递归，整段标记剥完后区间与最终文本严格对齐；`**加粗**和*斜体*与++下划线++` 这类混排可无损往返。嵌套标记（如 `++**文字**++`）按「同一字符只保留一种样式（加粗 > 斜体 > 下划线）」裁剪，保证数据、编辑面与 Markdown 视图三者一致。
- **修掉两个真 bug**：① 工具栏只改样式时没有回写应用层，store 随后拿旧值把编辑面里的样式覆盖回去；② 存储校验的行内样式白名单漏了 `underline`，导致下划线在回写时被丢弃。两者都由浏览器检查抓出来，现在校验器直接复用样式词表。

### 第四阶段后的差异清单

| 项 | 官方 | 本项目当前 | 状态 |
| --- | --- | --- | --- |
| 字号 A± | 移动端有（网页版没有） | 便签级档位，编辑器/预览/PNG/公众号一致 | 已对齐移动端语义 |
| 下划线 | 移动端有（网页版无语法） | `++文字++` 方言，预览/PNG/公众号一致 | 已实现（方言为本项目扩展） |
| 富文本粘贴 | 网页版按纯文本粘贴 | 按纯文本粘贴 | 与官方网页版一致 |
| 真机 | 原生客户端 | 开发机 390 px 已验证工具栏与字号按钮，真机未验收 | 待真机 |

仍不做且不建议做的：逐段字号与逐段颜色。它们是官方移动端的原生富文本能力，要落进 Markdown 方言会同时污染渲染、公众号内联样式与 Skill 接口，收益低于风险；便签字号档位已经覆盖了 A± 的真实语义。

## 13. 第六阶段：编辑器基础排版补齐（0.7.8）

本阶段只加入可以直接落在现有 Markdown/富文本真源上的能力，避免在统一内容模型完成前引入颜色、附件、表格等第二套数据结构：

- 行内删除线使用 `~~文字~~`，行内代码使用 `` `code` ``；两者都进入富文本样式区间，编辑面有对应装饰，Markdown 视图、PNG、公众号与归档继续沿用同一语法。
- Markdown 快速输入栏增加分隔线 `---` 与清除格式；清除格式会移除当前选区的常见字符标记，并清除当前行的标题、列表、待办和引用前缀。
- 富文本工具栏增加删除线和行内代码；快捷键为 `Cmd/Ctrl + Shift + X` 和 `Cmd/Ctrl + \``。移动端工具栏保持横向滚动，不压缩正文。
- NAS/电脑图片入口分开：电脑本地沿用浏览器文件选择器；NAS 本地使用飞牛文件选择器，服务端只读取当前用户已授权目录内的图片，大小限制为 32MB。

颜色、高亮、可视化表格、附件块、折叠块、内容块拖拽和自由画布需要把当前「Markdown + 富文本样式区间」逐步升级为带稳定 block ID 的统一内容模型，等模型迁移后再加入，避免编辑、预览、PNG、公众号和归档出现不同步。

## 14. 第七阶段：清除格式与富文本图片粘贴（0.7.9）

- **清除所选格式**：富文本工具栏增加第十一个按钮。它按选区覆盖的整行清除标题、居中、列表、待办、引用和全部行内标记，正文不变；Markdown 模式原有的清除格式入口继续保留。
- **粘贴与拖入图片**：富文本编辑面现在同时识别剪贴板里的图片文件、网页图片地址和拖入的图片文件。文件仍走 `/api/images/import`，NAS 图片仍由 `/api/read-image` 校验授权目录；导入后写成图片区块，预览、PNG、公众号和归档继续从同一份 Markdown 派生。

这两项都只在现有「文本 + 样式区间」模型内工作。颜色、高亮、可视化表格、附件、折叠块和块拖拽仍需要稳定的内容块模型，暂不在现有 Markdown 单一真源上硬加。
